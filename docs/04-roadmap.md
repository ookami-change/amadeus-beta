# 04 路线图与风险

## 1. 策略

**先打通最难的链路，再逐层加真实感。** 每个里程碑结束时都有一个可以实际对话的版本，并且都用 [真实感规范](01-product-and-realism.md#4-真实感规范可验收) 里的指标验收。

工期按 1–2 人投入估算，仅作量级参考。

## 2. 里程碑

### M0 技术验证（约 2 周）

目的：在写正式代码前，回答三个决定成败的问题。

| 验证项 | 要回答的问题 | 产出 |
|---|---|---|
| 语音链路延迟 | 中文下级联链路能否做到 P50 ≤ 800ms？ | 2–3 组 ASR/LLM/TTS 组合的实测延迟表 |
| TTS 表现力 | 哪个 TTS 能做出不像朗读的角色音？ | 同一批台词的试听对比，选定方案 |
| 形象渲染 | VRM 在浏览器里观感和性能是否达标？ | 一个带待机动画和口型的可旋转 demo |

**出口条件**：三项都有"可行"的结论和选定方案；否则调整架构（例如改用端到端语音模型、或改用原生客户端）。

### M1 能对话（约 3–4 周）

- 仓库脚手架：`apps/web`、`services/agent`、`packages/protocol`
- 全流式语音链路 + 可打断
- 人设 v1（提示词 + 口语输出规范）
- 形象：L0 生命感 + 口型 + 基础视线
- **验收**：T1、T3、S1、S2、B1；能连续聊 10 分钟不出戏

### M2 有身体（约 4–5 周）

- 表演脚本格式 + 解析 + 时间对齐
- 完整动画分层（L1–L6），首批动作库（约 30–50 个片段）
- 倾听行为：点头、附和、视线
- 情绪状态模型，联动表情/姿态/TTS
- "身体先行"的即时反应
- **验收**：T2、B2–B6、C2；静音观看也能看出她在听还是在说、心情如何

### M3 有记忆（约 4 周）

- 记忆库 schema、在线提取、会话后巩固
- 检索并注入上下文；常驻档案
- 待续事项 + 开场准备
- 记忆查看/删除界面
- **验收**：C3、C4、I2、I3；记忆评测集召回率达标

### M4 像个人（约 4 周，之后持续）

- 语义断句调优、附和声、推测式生成
- 快慢双脑 + 联网搜索
- 沉默处理与主动开口
- 遗忘与回忆的模糊表达
- 自我记忆与观点一致性
- **验收**：全部规范项；盲评（见 §3）

### M5 之后（方向，不排期）

- 视觉：摄像头看到用户（表情、是否在场），真正的眼神接触
- 桌面常驻形态 / 移动端
- 生成式手势与全身动作
- 正式定制的模型与声线
- 本地推理档

## 3. 评测体系

放在 `evals/`，从 M1 起随功能同步建设。

- **延迟基准**：自动化脚本播放录音，测端到端各环节耗时，每次改动链路后回归
- **记忆评测集**：见 [03 §7](03-memory.md#7-评测)
- **真实感评审**：固定的对话剧本（寒暄、深聊、打断、沉默、惹她生气、隔天回访），评审者按规范逐项打分。每个里程碑录屏存档以便对比
- **出戏日志**：日常试用中任何"这一下很 AI"的瞬间都记下来并归因（节奏 / 语言 / 身体 / 一致性）。这份日志是 M4 的主要工作清单

## 4. 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 中文流式链路延迟不达标 | 真实感根基不成立 | M0 最先验证；备选端到端语音模型或混合方案 |
| TTS 情感表现不足 / 角色音不自然 | "一开口就出戏" | M0 重点对比；预留自训练声线的时间 |
| 动作资产工作量大、质量差则显廉价 | 身体表现拖后腿 | 程序化优先，片段库小而精；宁缺毋滥 |
| LLM 人格漂移、回到助手腔 | 一致性崩坏 | 人设示例对白 + 输出检查 + 出戏日志驱动迭代 |
| 记忆检索错误（张冠李戴） | 信任崩坏，比不记得更糟 | 置信度门槛 + 模糊表达；宁可不提也不乱提 |
| 运行成本（长时语音 + 多模型） | 无法日常使用 | 提示词缓存、快慢分层、远期本地推理 |
| 版权（原作角色形象与声线） | 无法公开发布 | 人设/模型/声线可替换，默认原创，见下 |
| 情感依赖与用户福祉 | 伦理风险 | 她鼓励用户的现实生活与人际关系；不设计成瘾机制（无签到、无挽留话术） |

## 5. 待你决策

以下事项会改变后续工作，每项附了建议。未答复前按建议推进。

1. **角色与版权** —— 直接做原作角色，还是原创角色？
   建议：系统做成可替换，仓库默认原创角色。若只是个人自用可自行加载人设，但公开发布必须原创或取得授权。不克隆声优的声音。
2. **形象形式** —— 3D VRM 还是 Live2D？
   建议：3D VRM（全身实时动作的硬需求）。
3. **首发平台** —— Web、桌面还是移动端？
   建议：Web 优先，之后套壳成桌面常驻应用。
4. **语言** —— 中文对话配中文语音，还是日语语音 + 字幕？
   建议：中文语音。日语语音更贴原作，但"听 + 读字幕"会破坏实时对话感。
5. **部署** —— 云端 API 还是尽量本地？
   建议：v1 全云端保证质量，架构上保留替换能力。
6. **团队与投入** —— 几个人、是否有美术/动画资源？
   这决定 M2 的动作资产和正式模型怎么来（自制 / 外包 / 用公开素材）。

## 6. 下一步

M0 的三项技术验证可以并行开始。最先动手的应该是**语音链路延迟实测**，因为它的结论可能改变整体架构。
