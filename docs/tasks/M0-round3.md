## PR #5 评审

**R1：通过。** `.env.tpl` 全是 `op://` 引用，README 的命令改成了 `op run`，服务器上用 npmmirror 装 Python 3.12 的方法写清楚了。

**R5：通过，结论清楚。**

- `qwen3.8-flash` 单测首 token P50 443ms，三家里最快。GLM 有 2.2 秒，MiniMax-M3 是 713ms，都不进候选
- 连接复用没带来收益，这条从 R6 里去掉
- **疑点**：同一个模型，级联里首 token P50 是 689ms，单测只有 443ms，差了约 250ms。R6 要查清楚这 250ms 去哪了（并发的识别 / 合成连接？测量起点不同？不同的用户句？）
- 豆包低延迟档仍然没开通，混元没有密钥。见 R0b

**R3：方法有两个问题，结论暂不采纳。**

1. **语料不能用来测音频类模型。** `generate_turns.py` 把每句的前半句（例如"杯子我都擦过了，然后"）单独用 TTS 合成，再拼上静音。TTS 会把每个片段当成完整句子来读，句尾语调下沉。听起来就像"说完了"，Smart Turn 这类看语调的模型被误导是意料之中。真人说"然后……"时是拖音或上扬的。**话轮检测必须用真人录音。**
2. **误抢话的统计口径太窄。** 现在只算"落在标注停顿里"的。Smart Turn 有 13/20 在更早的短间隙上被判成说完，假设文本还只是"杯子我"。对用户来说，这同样是被抢话。以后**在真实说完之前判定结束，一律算误抢话**，标注停顿只用来做细分统计。

按新口径，三个方案都远高于 5%：固定 500ms 15/20，Smart Turn 13/20，LiveKit 18/20。但因为语料有偏，这组数字不能用来淘汰任何方案，只能说明要换语料重测。

   - 用手机或电脑麦克风，在安静的房间录
   - 照着 `evals/latency/turn_script.py` 的 20 句说，再加 20 句自由发挥的、像跟人聊天时那样边想边说的话（中间有"嗯""然后""就是"，有自然的停顿）

   - 每句一个文件，按 Cursor 给的编号命名；找家人或朋友再录一套会更好（不同的人语速和停顿习惯不同）

## R3b 话轮检测重测（Cursor，等录音）

1. **先给录音工具**：在 `evals/latency/turns/record/` 放一份录音清单（编号 + 文本 + 说明）和一个本地网页录音工具（浏览器录音，按编号保存 16kHz 单声道 wav），方便负责人一句一句录。录音工具在本地打开即可，不需要部署
2. **标注**：每条录音标出真实说完的时刻和句中停顿的区间。可以先用 VAD + 强制对齐自动标，再人工抽查
3. **统计口径**：误抢话 = 在真实说完之前判定结束，一律计入；另外细分"落在句中停顿里"和"落在更短的间隙里"。端点滞后只统计没有误抢话的样本
4. **方案**：固定 500ms、固定 800ms、Smart Turn、LiveKit 文本模型，加上组合策略（例如 Smart Turn 和文本模型都判说完才结束；静音 1200ms 强制结束）。豆包流式识别的服务端断句参数也测一组
5. **把合成语料的结果留着**，在报告里注明"合成语料对音频模型有偏，不作结论依据"

**验收**：误抢话 ≤ 5% 的方案里选端点滞后最低的。没有方案达标就照实写，并给出误抢话率和滞后的权衡曲线（阈值从低到高扫一遍）。
