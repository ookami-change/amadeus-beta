# M1 任务单：能对话

M0 的结论见 `docs/04-roadmap.md` §6，实测数据见 `evals/latency/REPORT.md`。

M1 要交付一个能在浏览器里和克劳德连续聊 10 分钟的版本：
- 全流式语音，可以打断；
- 人设 v1；
- 示例形象，带待机、口型和基础视线。

agent-bus 暂停期间，代码由架构师直接写，负责人做试用和真机测量。

## 验收目标

| 编号 | 指标 | M1 临时目标 | 最终目标 |
|---|---|---|---|
| T1 | 用户说完到她出声 | P50 ≤ 1450ms、P95 ≤ 3000ms（负责人 2026-11-24 定） | P50 ≤ 800ms、P95 ≤ 1500ms |
| T4 | 误抢话 | ≤ 10% | ≤ 5% |
| T3 | 被打断后停下 | ≤ 200ms，并有反应 | 同左 |
| S1、S2 | 回复长度、口语 | 见 `01-product-and-realism.md` §4.2 | 同左 |
| B1 | 待机不静止、不循环 | 见 `01-product-and-realism.md` §4.3 | 同左 |

除表中指标外，负责人要能连续聊 10 分钟，不出戏。

## 链路（已定）

- **供应商**：豆包流式识别 + `qwen3.8-flash` + MiniMax `speech-2.8-turbo`，音色用 Intellectual Girl。
- **断句**：S1「短 1400 / 长 1800」。
- **起跑**：静音 400ms 时提前起跑。
- **播放**：等到断句点再播。
- **合成连接**：预热一条，没出声就复用。

详见 `02-architecture.md` §2.2「M1 的实际做法」。参考实现是 `evals/latency/early_live.py`，它的实测结果是误抢话 5/50，P50 1422ms，P95 2277ms。

## M1-1 协议和传输

**范围**

- 在 `packages/protocol` 定 v0.1 消息表，覆盖：
  - 会话开始和结束；
  - 识别的中间结果和定稿；
  - 导演状态：待机 / 倾听 / 思考 / 说话 / 被打断；
  - 「准备开口」（给 T2 留口子）；
  - 一句话的开始和结束，结束时带实际播到的位置；
  - 口型时间。
- TypeScript 和 Python 两边共用一份定义。
- **传输先用 WebSocket**：浏览器用 `getUserMedia` 自带的回声消除，16kHz PCM 上行，合成音频下行。
  - 只服务一个用户、一台上海服务器时，WebSocket 最简单。
  - 回声或抖动不合格时再换 WebRTC / LiveKit，换的时候只动传输这一层。

**验收**

- 两边的单元测试用同一组样例消息，序列化后互相能读。
- 负责人在手机和笔记本上各连一次，记录浏览器到服务器的往返时间。
- 外放播放时，她自己的声音不会被识别成用户说话。

## M1-2 服务端语音链路

**范围**

- 把 `evals/latency/adapters` 里的豆包识别、Qwen、MiniMax 适配器搬进 `services/agent`。
- 修掉 R6b 暴露的问题：
  - LLM 复用一个 HTTP 客户端，现在每次调用都新建 `httpx.AsyncClient`；
  - 取消生成时把异步生成器收干净，R6b 有 28 次 `aclose()` 警告；
  - MiniMax 限流闸门按合成任务计数，不只按开连接；
  - 可重试错误自动重试，不能重试的要让她说一句「刚才没听清」之类的话，不能静默。
- 按 R6b 的做法接起断句、提前起跑、等断句再播和合成连接复用。

**验收**

- 用 50 条真人录音经 WebSocket 回放，跑完整服务。要求：
  - 误抢话 ≤ 5/50；
  - P50 ≤ 1450ms，P95 ≤ 3000ms；
  - 失败 ≤ 1/50。
- LLM 首 token 的 P95 和 R6b 同场串行的 1560ms 对比，写进报告。
- 新代码过 lint、mypy strict 和单元测试，包括取消和重来的路径。

**不做**：慢脑、记忆、工具调用。

## M1-3 打断和让话（T3）

**范围**

- **她说话时用户出声：**
  - 附和声（「嗯」「对」，短于约 600ms、文字在附和词表里）不打断；
  - 其他情况 200ms 内停止播放，状态转到「被打断」，并带一个反应：停顿，或「啊，你说」。
- **让话**：剩下的误抢话都是「话已经完整、停一下又补一句」。她刚开口约 1.5 秒内用户又说话时，马上停下，并把两段话合起来重新回答。
- **上下文**：对话历史里只记实际播出去的部分（`02-architecture.md` §2.3）。

**验收**

- 用 R6b 的 5 条误抢话录音（f02、f03、f10、f11、f12）回放：每条都在 200ms 内停下，第二次回答用的是合并后的完整句子。
- 10 条附和声样本不打断，10 条真打断样本都停下。
- 打断后，历史里那一句的文字截到实际播放的位置。

## M1-4 人设 v1（S1、S2）

**范围**

- 写克劳德的系统提示和口语输出规范，依据 `01-product-and-realism.md` §4.2、§5.2：
  - 默认 1–3 句，不分点；
  - 犹豫靠停顿和「嗯……」。
- 情绪参数映射按 `02-architecture.md` §3.2 的护栏来。
- 准备 30 条测试用的用户句子：寒暄、闲聊、提问、要她讲解，以及她该拒绝的。

**验收**

- 30 条的回复由负责人盲评，「像她」≥ 24 条。
- 自动检查不出现以下情况：分点、「首先」、「总之」、「还有什么可以帮你」。
- 非讲解类的回复不超过 3 句。

## M1-5 网页客户端

**范围**

- 一个页面就能对话：
  - 麦克风采集；
  - 按音频播放时钟播放；
  - 显示识别文字（调试用，可以关掉）。
- 形象用示例模型，沿用 D3、R4a 的代码：
  - L0 生命感；
  - 口型，先用音频驱动；
  - 基础视线：倾听时看用户，思考时移开。
- 收到「准备开口」时先有身体反应，这是 T2 的起点，M1 不验收 T2。
- 在客户端测量端到端延迟：用户说完由客户端 VAD 判断，到第一帧音频真正播出，上报服务端。

**验收**

- 负责人的笔记本和手机都能打开并对话。
- 客户端测到的 T1 和服务端的数相差不超过 150ms，超了就找出原因。
- B1：待机 5 分钟，负责人看不出循环。

**依赖**：R4 的真机帧率数据决定渲染档位；克劳德正式模型（A8）到位前用示例模型。

## M1-6 整体验收

**范围**

- 负责人用 M1 版本聊 3 次，每次 10 分钟，服务端记日志：每轮的断句、起跑、取消、重来、首 token、首音频和打断。
- 架构师根据日志写 M1 报告，对照上面的验收表逐项给结论。

**验收**

- 3 次里至少 2 次聊满 10 分钟不出戏，由负责人判断。
- T1、T4、T3 用这 3 次的真实对话计算，不用录音回放的数。

## 留到 M1 之后

- LiveKit 文本模型做断句，需要一批没参与挑阈值的新录音来验证。
- LLM 首 token 对冲：超过约 900ms 再发一次请求。先看 M1-2 复用连接以后的长尾还剩多少。
- 慢脑、记忆、表演脚本，见 M2、M3。
