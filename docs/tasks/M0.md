# M0 任务单：技术验证

目的：在写正式代码前，用实测回答三个决定架构的问题。M0 的产出是**数据和结论**，代码是一次性的测量工具，够用即可，不要过度设计。

四个任务中 D0 先做，D1–D3 可并行。优先级：**D1 > D2 > D3**。

需要项目所有者提供：火山引擎、阿里云百炼、MiniMax 的 API 密钥（项目走国内线，见 `docs/06-vendors.md` §4）。

## D1 语音链路延迟实测

**要回答的问题**：中文对话下，级联链路（断句 → ASR → LLM → TTS）从用户说完到首个音频包，P50 能否 ≤ 800ms、P95 能否 ≤ 1500ms？哪组供应商组合最优？

**前置**：每类至少 2 家候选的密钥。候选与首轮组合见 `docs/06-vendors.md` §4，可补充你认为值得测的。测试机须在国内，报告里注明所在地区与网络。

**范围**（放在 `evals/latency/`）

1. **适配器接口**：ASR、LLM、TTS 各定义一个流式接口，每家供应商一个实现。这套接口会被 M1 沿用，值得认真设计
2. **测试语料**：20 条中文口语录音（16kHz 单声道），覆盖：短寒暄（3 条）、普通陈述（8 条）、句中有明显停顿的长句（5 条）、提问（4 条）。可用 TTS 合成或真人录制，文本与音频都入库
3. **测量脚本**：把录音按实时速率流式送入链路，对每条记录各环节时间戳：
   - `t_speech_end` 录音中语音实际结束时刻
   - `t_endpoint` 断句判定时刻
   - `t_asr_final` ASR 定稿时刻
   - `t_llm_first_token` LLM 首 token
   - `t_llm_first_clause` LLM 首个可送 TTS 的子句完成
   - `t_tts_first_audio` TTS 首个音频包
4. **LLM 提示词**：使用固定的人设短提示词（约 1500 字，任务内自拟一份占位即可）+ 4 轮历史，开启提示词缓存，输出限制为 1–2 句口语
5. **断句对比**：至少对比"固定静音阈值 500ms"与"语义断句模型"两种方式，统计误抢话率（在句中停顿处误判为结束的比例，用那 5 条长句测）
6. **每个组合跑 3 遍**，报告 P50 / P95

**交付物**

- `evals/latency/` 代码与语料
- `evals/latency/REPORT.md`：
  - 各组合的分环节延迟表（P50 / P95）
  - 端到端 `t_tts_first_audio − t_speech_end` 的排名
  - 断句方式对比（延迟 + 误抢话率）
  - 测试环境说明（所在地域、网络、日期）
  - 你的推荐组合与理由

**验收**

- 至少 2×2×2 = 8 个组合有完整数据
- 测量脚本可一条命令复现
- 报告如实给出数字；达不到 800ms 也照实写，并指出瓶颈在哪一环

**不做**：WebRTC、打断处理、任何 UI。直接在本机进程内串联即可（网络传输延迟留到 M1 测）。

## D2 语音合成表现力对比

**要回答的问题**：哪个 TTS 能把角色台词说得不像朗读？

**前置**：与 D1 相同的 TTS 密钥；可复用 D1 的 TTS 适配器。

**范围**（放在 `evals/tts/`）

对每个候选 TTS，合成下面全部台词。角色是克劳德（设定见 `docs/01-product-and-realism.md` §5.2）：选音色时挑最接近"年轻女声、安静、温和、吐字清楚、略带书卷气"的预置音色，**不要**甜腻或元气型。支持情绪 / 风格控制的，按提示设置；不支持的直接合成。

她的情绪幅度小，所以这组台词考的是**细微差别**：平静里的一点高兴、克制的笑、小声的害羞。能把这些说出区别的才算合格。

| 编号 | 台词 | 情绪提示 |
|---|---|---|
| 1 | 店长，你来了。 | 平静，带一点不易察觉的高兴 |
| 2 | 等一下，这个数字不对。 | 较真，认真但不凶 |
| 3 | 嗯……这个我没有把握，让我想一想。 | 思考，语速放慢，有停顿 |
| 4 | 不是，我的意思是——理论上可以，只是没有人会这样做。 | 自我修正，语速略快 |
| 5 | 这个我知道。要听吗？可能会有点长。 | 克制的期待 |
| 6 | 诶？真的吗？ | 惊讶，但声音不大 |
| 7 | ……这句话，你听了就忘掉吧。 | 害羞，声音变小 |
| 8 | 已经这么晚了。你明天不是要面试吗，该睡了。 | 关心，平静而坚持 |
| 9 | 嗯。 | 附和声，很短，表示在听 |
| 10 | 呵……抱歉，这个有点好笑。 | 忍不住的轻笑，随即收住 |
| 11 | 唉……好吧，这次就算了。 | 轻叹，让步 |
| 12 | 所以严格来说，时间并不是像我们感觉的那样在"流动"。物理上它只是一个坐标，是大脑在整理记忆的时候，才给了它方向。……抱歉，我是不是说得太多了。 | 讲到兴头上语速渐快、有重音，最后一句收住，略不好意思 |
| 13 | 上次你说的那件事，我记下来了。 | 轻，认真，有一点高兴 |
| 14 | 对不起，刚才是我说得太重了。 | 低落，真诚 |

**交付物**

- `evals/tts/out/{供应商}/{编号}.wav`
- `evals/tts/index.html`：一个静态试听页，行是台词、列是供应商，点击播放，方便横向对比
- `evals/tts/REPORT.md`：每家的首包延迟、是否支持流式输入、是否支持情绪控制 / 笑声叹气等非语言声音、是否返回音素或字级时间戳（口型同步要用）、是否支持声线定制、计费方式

**验收**

- 至少 3 家候选，14 条全部合成
- 试听页本地双击可用
- 报告只陈述事实与能力矩阵；最终选型由负责人和架构师试听后决定

## D3 形象渲染验证

**要回答的问题**：VRM 模型在浏览器里的观感和性能是否达标？待机"生命感"靠程序化能做到什么程度？

**前置**：一个许可允许使用的公开示例 VRM 1.0 模型（来源与许可写进 README；模型文件不大的话可入库，否则给下载脚本）。

**范围**（放在 `apps/web`，作为一个独立 demo 页）

1. 加载 VRM 并全身显示，卡通材质正常，纯色或渐变背景，相机固定在全身构图
2. **程序化待机**（不使用任何预制动画片段）：
   - 呼吸：胸腔与肩的周期运动，周期带随机抖动
   - 眨眼：间隔随机（2–6 秒），偶尔连眨两次
   - 微眼动：视线小幅跳动
   - 重心转移：每 8–20 秒髋部与脊柱缓慢偏移一次
   - 头部微动：低幅噪声驱动
3. **视线跟随**：眼睛和头部跟随鼠标位置，头部有延迟和幅度上限，眼睛先动头后动
4. **口型**：页面上能播放一段音频（用 D2 产出的某条即可），口型随之开合。实现音频驱动的 5 元音口型估计；如果 D2 中有供应商返回时间戳，另做一版时间戳驱动的对比
5. **性能面板**：显示帧率与每帧耗时

**交付物**

- 可本地运行的 demo
- `apps/web/M0_REPORT.md`：在至少一台普通笔记本（集成显卡）和一台手机上的帧率；两种口型方案的主观对比；遇到的 three-vrm 限制
- 一段 30 秒录屏

**验收**

- 集成显卡笔记本上 ≥ 60fps，手机上 ≥ 30fps
- 待机状态连续观看 60 秒，看不出循环点
- 视线跟随不出现头部瞬移或眼球翻白

**不做**：手势、表情切换、与服务端的任何连接。
